## 2. 可以吸收的内容

### 2.1 事项中心复用思路

“我的工作台”提出引用事项中心页面，按信息公开应用筛选，并附有事项中心截图。这为统一待办与工作台的关系提供了可讨论的复用方向。

### 2.2 业务运行流程图中的补充线索

图片包含正文未充分说明的节点和分支：

- 公开属性审核与政策解读、舆情应对方案、删减后公开版本等配套审核的关系。
- 是否联合发文以及转出会签。
- 拟签发文件、文件归档及按公开属性进入不同处理路径。
- 申请内容是否明确完整、拟办形式、是否涉及第三方利益、书面意见征集及第三方审查。
- 拟定答复之后的法律审查、延期审批／告知、出具答复书及申请人签收。
- 申请人不服后的行政复议、行政诉讼分支。

这些是新增调研线索，尚需逐项确认：是本系统办理、关联其他系统、线下办理，还是只登记结果。特别是会签、复议和诉讼，不能仅凭图片就扩展为本系统新增子模块。

流程图将发文公开属性处理和依申请公开放在同一总图中。正式需求建议先按两类业务分别画清主流程，再通过公文及申请对象的关联关系连接，避免误解为所有公开申请都必须从部门起草公文开始。

## 4. 字段和操作中应纠正的具体问题

1. **证件号码来源不合理。** 申请表将证件号码写成“自动生成、不可编辑”“默认身份证号不可修改”，未说明数据来源。证件号码不是业务流水号，应按网上传入、人工登记或有依据的身份信息带入分别确定。
2. **答复日期规则未经确认。** 申请表写“默认增加20天”，但起算日、自然日／工作日、补正影响及延期关系均未说明。Excel也未规定首次答复期限；该默认值应退回待确认，本文不对其法律适用性下结论。
3. **按钮名称与行为不相符。** “生成延期回执”对应人工录入信息公开详情，“生成公开答复”仅对应查看申请详情；没有说明创建关联申请、审签及生成文书的实际行为。
4. **公报导入边界矛盾。** 文件筛选说明“无人工导入”，通用操作却包含“导入”。应先确定允许的数据渠道，再列按钮。
5. **系统外省直部门入口被提前确定。** Word直接写“为不在系统内的省直部门提供在线填报入口”，Excel只要求省直部门在线填报，同时将系统外单位留待调研。外部单位账号、登录和授权范围尚需确认。
6. **有效期归属不清。** 标签表把“有效期”放在标签上，但规范性文件有效期可能属于文件及其效力关系；不能以标签日期直接代替每份文件的有效期规则。
7. **列表和详情边界不清。** 将证件号码、全部联系方式、长文本说明等全量列为申请列表字段，且统一“全字段筛选”。应按使用角色和办理任务确定摘要列、详情字段、检索范围及敏感信息显示方式。
8. **文书名称不统一。** “延期回执”“政府信息延期答复书”“延期答复通知书”等混用，应核实它们是否指同一文书，统一模板名称和生成节点。

以上并非建议直接增加这些字段或功能，而是要求先明确业务含义和数据来源。

## 5. 关联性应如何补齐

### 5.1 公文认定与公开结果

来源公文 → 公开属性认定及依据 → 审核复核 → 原稿／删减后公开稿／政策解读等关联材料 → 发文或签报完成 → 向门户推送并同步本模块。

需补齐来源公文标识、最终公开属性、各版本用途、同步触发、发布结果及可见范围。公报候选文件可来自相关公文结果，但是否所有公开文件都可入选公报，应另定筛选规则。

### 5.2 依申请公开主业务

来源申请 → 受理登记 → 内容审核／补正 → 拟办及协同／征求意见 → 拟定答复 → 答复审签或延期审签 → 生成文书 → 对外送达 → 归档。

关键关系是“同一申请下的多次处理记录及关联审批”，而不只是多个页面之间可以点击跳转。需说明关联标识、带入字段、当前办理状态、审批退回后的处理、延期对截止日期的影响、送达记录及归档材料。法律审查、第三方意见等图片新增节点应确认后纳入。

### 5.3 政府公报

来源文件 → 标签／备选 → 一期制作所选文件 → 排版任务及返回文件 → 校验记录 → 各渠道发布记录。

需要区分单个文件、一期公报、排版结果和渠道发布记录。仅有一个“已发布／未发布”字段，无法说明一期多文件、多渠道的结果；是否允许部分成功及如何重发，应确认后定义。

### 5.4 政务信息编报

约稿通知 → 对应报送记录 → 共享／备选选稿 → 刊物及采编稿 → 分类审核 → 刊物库 → 发布记录 → 取消／删除／回收及恢复。

需保留原始报送与采用稿的关联，并确认一条报送是否可多次采用、采用状态如何反馈、修改是否影响已经发布的刊物，以及恢复恢复到哪个状态。“通知”不能替代“报送记录”，“刊物库”也不能替代“发布记录”。

### 5.5 群众需求与公共入口

来源渠道 → 采集记录 → 导入批次或来源标识 → 查询和维护；首页仅汇总有业务口径的数据。当前没有依据把群众采集自动转成信息公开申请、公报文件或编报稿件。

公共关联还包括：角色决定数据和按钮可见范围，业务状态决定可执行动作，流程节点决定待办，已确认的时限决定临期提醒，外部处理回执决定接收／发布／归档结果。

## 6. 文档结构与格式调整建议

- 目录与正文使用一致的标题层级和编号。当前目录列了3.3依申请公开，正文又出现3.1依申请公开；部分标题和流程正文混在同一普通段落中。
- 目录条目统一使用了同一种TOC样式，且保存的目录页码均显示1；需在正文结构修正后重新生成和更新目录，不能把这些缓存页码当成真实页码。
- 统一编号规则，避免正文引用“5.2.2”“5.3.5”但对应标题未建立明确编号。
- 每个业务先讲目标、对象、参与者及完整流程，再描述页面与操作。避免只按“列表—新建—详情”拆开，导致同一业务关系被割裂。
- 列表字段用列表字段表，表单用字段定义表，按钮用操作条件及结果表；无需把每个列表都重复写成表单输入要求。
- “无审批”“无外部集成”仅在业务上确认不涉及时使用；未明确的内容写待确认，并关联具体问题。
- 清理空表、占位语句、重复段落和错误文书名；流程图中的有效信息应转换成正文规则，而非仅贴图。
- 继续采用原梳理稿建议的总章节框架，优先加强业务流程、业务对象关系、公共规则及接口边界，不宜只修字体和表格。

本次核实了结构性格式问题并查看内嵌图片；未完成Word整篇分页视觉检查。尝试使用文档技能的渲染器时，环境未找到LibreOffice soffice.exe，因而不对断页、表格跨页、字形或内容溢出作结论。

## 7. 后续整理时的材料采用规则

Excel保留为初始调研来源，Word v2作为补充来源；二者冲突时记录差异，等待业务确认，不默认以文件日期或版本号决定业务结论。

可立即吸收事项中心复用线索、流程图中的待确认节点、业务对象关联及字段草案。应纠正错误按钮映射、数据去向和文书名称，补齐遗漏模块。时限、审签人、外部单位填报、审核节点及接口能力均保持待确认。

下一版需求说明书应将每条需求关联到“业务对象—参与角色—流程节点—页面动作—数据变化—外部协同—验收场景”，再进入原型和技术设计。
